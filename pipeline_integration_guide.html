Squad 2 triggers Squad 3's full processing pipeline (Steps 3–6) as a background async task. Squad 3 exposes their pipeline as a callable Python function. The exact inputs, outputs, and error signals must be agreed before either squad writes integration code.
The agreed function contract — to be confirmed in meeting
# Squad 3 exposes this function — Squad 2 calls it
def process_video(
  gcs_path: str, # full GCS path to raw video
  analysis_id: str # uuid — used for naming output files in GCS
) -> dict:
  # Runs Steps 3, 4, 5, 6 internally
  # On success returns:
  return {
    "status": "success",
    "overlay_video_url": "gs://...", # Step 5 output — sent to Nemotron
    "biomechanics_json": { ... }, # Step 6 output — stored in DB
  }
  # On quality gate failure returns:
  return {
    "status": "failed",
    "error_code": "BAD_ANGLE", # BAD_ANGLE / LOW_CONFIDENCE / PARTIAL_OCCLUSION / VIDEO_TOO_SHORT
    "affected_landmarks": ["left_knee"] # which joints failed visibility check
  }
What Squad 2 does with the return value
On success: stores biomechanics_json to DB · sends overlay_video_url to Nemotron · emits biomechanics_complete SSE
On failure: updates form_sessions status to "failed" · emits error SSE event with error_code and retryable: false
SSE events during Steps 3–6 — developer recommendation needed  Ask Nicole + Anusha/Ezequiel
Squad 2 owns the SSE stream. Squad 3 runs the pipeline. The question is how Squad 3 signals progress back to Squad 2 so intermediate SSE events can fire. Below are three options from simplest to most robust — ask the developer which they recommend and why before deciding.
Option C · Simplest Single call — Squad 2 fires SSE only at start and end
Squad 3 is one blocking function call. Squad 2 emits mediapipe_started before and biomechanics_complete after. No intermediate events. Progress bar jumps from 10% → 33% in one step. Fastest to build. Trade-off: frontend progress is less granular for the user.
Option B · Medium Sequential calls — Squad 2 calls Squad 3 in stages
Squad 2 calls Squad 3 in three steps: run_mediapipe() → emit SSE → run_overlay() → emit SSE → run_biomechanics() → emit SSE. Squad 2 has full control but Squad 3 must expose three separate functions. Tighter coupling between squads.
Option A · Most robust Callback — Squad 3 signals Squad 2 at each internal stage
Squad 2 passes an emit_event(name, payload) callback into process_video(). Squad 3 calls it after each internal step. All four events fire in real time: mediapipe_complete · overlay_complete · biomechanics_complete. Squad 3 stays self-contained. Best user experience — live progress bar. Slightly more complex to wire initially.
Note for developer meeting: Present all three options. Ask Nicole (S2) and Anusha/Ezequiel (S3) which they can implement fastest given current progress. For a demo, Option C is acceptable. For a product, Option A is the right long-term architecture.

Step 4
Visibility quality gate
Squad 3 — Data / Full Stack · Runs immediately after Step 3
Squad 3
IN
Per-frame landmark visibility + presence scores from Step 3
OUT — pass
Pipeline continues to Step 5. All critical landmarks visible across ≥70% of frames.
OUT — fail
Returns error dict to Squad 2 with error_code and affected_landmarks. Pipeline stops. Squad 2 emits SSE error event and writes status: "failed" to DB.
Error codes Squad 3 must produce — Squad 2 maps these to SSE error events
BAD_ANGLE — camera angle prevents reliable landmark detection across key joints
LOW_CONFIDENCE — landmark visibility below threshold for >30% of frames
PARTIAL_OCCLUSION — one or more critical joints obscured (clothing, object in frame)
VIDEO_TOO_SHORT — fewer than 3 complete reps detected

Overlay spec — Option 3 scope (agreed)
Skeleton lines (hip→knee, knee→ankle) drawn using cv2.line — already built in Part 1

Gold standard comparison text alongside actual — e.g. "Ideal: 80–95°" in green
