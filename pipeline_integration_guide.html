SSE events during Steps 3–6 — developer recommendation needed  Ask Nicole + Anusha/Ezequiel
Squad 2 owns the SSE stream. Squad 3 runs the pipeline. The question is how Squad 3 signals progress back to Squad 2 so intermediate SSE events can fire. Below are three options from simplest to most robust — ask the developer which they recommend and why before deciding.
Option C · Simplest Single call — Squad 2 fires SSE only at start and end
Squad 3 is one blocking function call. Squad 2 emits mediapipe_started before and biomechanics_complete after. No intermediate events. Progress bar jumps from 10% → 33% in one step. Fastest to build. Trade-off: frontend progress is less granular for the user.
Option B · Medium Sequential calls — Squad 2 calls Squad 3 in stages
Squad 2 calls Squad 3 in three steps: run_mediapipe() → emit SSE → run_overlay() → emit SSE → run_biomechanics() → emit SSE. Squad 2 has full control but Squad 3 must expose three separate functions. Tighter coupling between squads.
Option A · Most robust Callback — Squad 3 signals Squad 2 at each internal stage
Squad 2 passes an emit_event(name, payload) callback into process_video(). Squad 3 calls it after each internal step. All four events fire in real time: mediapipe_complete · overlay_complete · biomechanics_complete. Squad 3 stays self-contained. Best user experience — live progress bar. Slightly more complex to wire initially.
Note for developer meeting: Present all three options. Ask Nicole (S2) and Anusha/Ezequiel (S3) which they can implement fastest given current progress. For a demo, Option C is acceptable. For a product, Option A is the right long-term architecture.

Section 3 — The data gap
Why OpenCV Step 2 cannot be built as the pipeline currently stands
OpenCV Step 2 needs to seek to the exact frame in the video where the worst rep hit its bottom position. To do that it needs bottom_timestamp_ms for that rep. Here is why that data is currently unavailable when it's needed.
The gap
MediaPipe computes bottom_frame and bottom_timestamp_ms for every rep during rep segmentation. This data exists in memory at Step 3 and is used immediately by:

  → OpenCV Step 1 (video overlay) — uses landmark positions to draw the skeleton
  → Biomechanics script — uses the timing to compute tempo data

But neither step saves the bottom_frame or bottom_timestamp_ms anywhere. Once Step 5 and Step 6 are done, the MediaPipe data is gone from memory.

By Step 8 (OpenCV Step 2), which runs after Nemotron at Step 7, there is no way to recover which frame number corresponds to rep 3's bottom position.
What the current biomechanics JSON schema has vs what's needed
The biomechanics JSON already stores rich per-rep data — angles, tempo, stability. The gap is two missing fields that MediaPipe computes but the schema doesn't capture.

Section 4 — Proposed change
What needs to change and who does it
The fix — one schema change, no new storage
No new tables, no new services. The biomechanics JSON is already saved to the DB. The fix is to include bottom_frame and bottom_timestamp_ms in each rep object when the biomechanics script writes its output.

MediaPipe already computes both values during rep segmentation — they just need to be passed through to the output JSON instead of being discarded.
Changes required — by squad
Squad 3 — Biomechanics script
When the biomechanics script processes each rep, it already has access to the rep's bottom_frame from MediaPipe's rep segmentation output. Add these two fields to the rep object before returning the JSON.
# In the rep segmentation loop — Squad 3 already computes this
for rep in segmented_reps:
  bottom_frame = rep.bottom_frame_index # already computed by MediaPipe
  bottom_timestamp_ms = (bottom_frame / fps) * 1000 # same formula as OpenCV wrapper
  
  rep_output = {
    "rep_number": rep.number,
    "bottom_frame": bottom_frame, # ADD THIS
    "bottom_timestamp_ms": bottom_timestamp_ms, # ADD THIS
    "tempo_data": ...,
    "depth_data": ...
  }
Squad 2 — Pipeline orchestration
After Nemotron returns per-rep scores, Squad 2 identifies the worst rep and queries the stored biomechanics JSON from the DB to get that rep's bottom_timestamp_ms. This is then passed to Squad 3's frame extraction function.

Section 5 — OpenCV capabilities research
What OpenCV can and cannot do for this overlay — and a second data gap
Research on the specific OpenCV functions needed, their limitations on real video frames, and an additional data requirement that only becomes visible when you try to implement the overlay.
5a — MediaPipe coordinates → pixel positions
MediaPipe outputs landmark positions as normalised floats (0.0–1.0) relative to the image dimensions — not pixel coordinates. Every OpenCV drawing function requires pixel integers. The conversion is one multiplication per axis, applied to every landmark before any drawing call.
# MediaPipe landmark for, say, the left knee
lm = results.pose_landmarks.landmark[mp_pose.PoseLandmark.LEFT_KNEE]

h, w, _ = frame.shape # frame height and width in pixels

knee_px = (int(lm.x * w), int(lm.y * h)) # → e.g. (382, 540)

# Repeat for hip and ankle — these three points define the knee angle
hip_px = (int(hip_lm.x * w), int(hip_lm.y * h))
ankle_px = (int(ankle_lm.x * w), int(ankle_lm.y * h))
⚠
Second data gap — landmark pixel positions at bottom_frame are not stored. The biomechanics JSON stores computed angle values (e.g. knee_angle_at_bottom: 88.2) but not the pixel coordinates of each joint at that specific frame. To draw the angle arc in the correct location on the image, the drawing code needs to know WHERE the knee is on the extracted frame — not just what the angle is. See Section 5e for options.
5b — OpenCV drawing functions available

5c — Drawing a joint angle arc with cv2.ellipse
The angle arc at a joint (e.g. the knee) is drawn at the joint pixel position, spanning from the direction of the lower limb (knee→ankle) to the direction of the upper limb (knee→hip). The key step is converting the limb directions to the angle convention that cv2.ellipse expects.
# Step 1 — calculate the angle at the joint (hip–knee–ankle)
import numpy as np

def joint_angle(a, b, c):
  """a = hip_px, b = knee_px (vertex), c = ankle_px"""
  a, b, c = np.array(a), np.array(b), np.array(c)
  radians = np.arctan2(c[1]-b[1], c[0]-b[0]) - np.arctan2(a[1]-b[1], a[0]-b[0])
  angle = np.abs(radians * 180.0 / np.pi)
  if angle > 180.0: angle = 360 - angle
  return angle

# Step 2 — compute the directions of each limb from the joint, in degrees
angle_to_hip = np.degrees(np.arctan2(hip_px[1] - knee_px[1], hip_px[0] - knee_px[0]))
angle_to_ankle = np.degrees(np.arctan2(ankle_px[1] - knee_px[1], ankle_px[0] - knee_px[0]))

# Step 3 — draw arc at the joint position
arc_radius = 30 # pixels — scale with image resolution
cv2.ellipse(
  frame,
  knee_px, # centre = joint pixel position
  (arc_radius, arc_radius), # axes (circle arc)
  0, # rotation of ellipse = 0
  min(angle_to_hip, angle_to_ankle), # startAngle
  max(angle_to_hip, angle_to_ankle), # endAngle
  (38, 191, 255), # colour — blue for actual
  2 # thickness
)

# Step 4 — draw angle value as text near the arc
angle_value = joint_angle(hip_px, knee_px, ankle_px)
label_pos = (knee_px[0] + arc_radius + 5, knee_px[1])
cv2.putText(frame, f"{angle_value:.0f}°", label_pos, cv2.FONT_HERSHEY_SIMPLEX, 0.6, (255,255,255), 2, cv2.LINE_AA)
Important: cv2.ellipse angles are clockwise from the 3 o'clock position — the same convention as screen coordinates (y-axis points down). arctan2 already works in this space so no further conversion is needed as long as you compute angles using pixel coordinates (not normalised ones).
5d — Text readability on real video frames
Real video frames have varied, unpredictable backgrounds — gym floors, walls, clothing. White text on a white wall is invisible. The standard pattern is a semi-transparent dark rectangle behind each text label, blended using cv2.addWeighted.
# Pattern: draw text with semi-transparent background
def draw_label(img, text, position, alpha=0.6):
  overlay = img.copy()
  
  # measure text size to size the background rectangle
  (tw, th), baseline = cv2.getTextSize(text, cv2.FONT_HERSHEY_SIMPLEX, 0.55, 1)
  x, y = position
  pad = 4
  
  # draw dark background on overlay copy
  cv2.rectangle(overlay, (x-pad, y-th-pad), (x+tw+pad, y+baseline+pad), (0, 0, 0), -1)
  
  # blend overlay back into image at given alpha (0 = transparent, 1 = opaque)
  cv2.addWeighted(overlay, alpha, img, 1-alpha, 0, img)
  
  # draw text on top of blended image
  cv2.putText(img, text, (x, y), cv2.FONT_HERSHEY_SIMPLEX, 0.55, (255,255,255), 1, cv2.LINE_AA)
Additional readability rules for real video
→ Font scale should be proportional to image height — not hardcoded. A scale of image_height / 720 * 0.6 keeps text the same visual size regardless of resolution.
→ Use cv2.LINE_AA on all text and line drawing calls for anti-aliased edges.
→ Always draw a white outline before drawing coloured text — draw the same text string in white at thickness+1 first, then draw the coloured text on top. This creates a visible border against any background.
→ Keep annotations away from the body — draw labels to the side of the joint, not on top of the limb. Offset the label position by arc_radius + 8px.
5e — Second data gap: landmark pixel positions needed for overlay placement
The gap
The biomechanics JSON stores computed angles (e.g. knee_angle_at_bottom: 88.2). To draw the angle arc in the right location on the extracted frame, OpenCV Step 2 also needs the pixel coordinates of each joint at that specific frame — i.e. where on the image is the knee, hip, and ankle. These are not stored anywhere. The biomechanics script computes angles from the landmarks but discards the raw positions.
Three options — bring to the developer meeting
Option A — Recommended
Re-run MediaPipe on the single extracted bottom frame
After seeking to bottom_timestamp_ms and extracting the frame, run MediaPipe Pose on that one image. MediaPipe is fast on a single frame (~50–100ms). This gives fresh, accurate pixel coordinates for all landmarks — no schema changes needed.
Pro: no additional stored data. Con: one extra MediaPipe call after Nemotron completes — small latency cost.
Option B
Store key landmark positions for bottom_frame in biomechanics JSON
Add a landmarks_at_bottom block to each rep in the biomechanics JSON — normalised x/y for left_knee, right_knee, left_hip, right_hip, left_ankle, right_ankle. These are already known at the time the biomechanics script runs.
"landmarks_at_bottom": {
  "left_knee": {"x": 0.48, "y": 0.71},
  "left_hip": {"x": 0.46, "y": 0.52},
  "left_ankle": {"x": 0.49, "y": 0.89}
}
Pro: no extra processing at frame extraction time. Con: larger biomechanics JSON, more schema changes needed.
Option C
Skip position-accurate arcs — use a fixed annotation panel
Instead of drawing arcs at the joint positions, add a fixed semi-transparent panel at the side or bottom of the image showing the three angle values as text. No landmark positions needed — uses only the computed angles already in the biomechanics JSON.
Pro: simplest implementation. Con: less informative — the user cannot see where on their body the issue is. Not recommended for the Results screen.

5a — MediaPipe coordinates → pixel positions
MediaPipe outputs landmark positions as normalised floats (0.0–1.0) relative to the image dimensions — not pixel coordinates. Every OpenCV drawing function requires pixel integers. The conversion is one multiplication per axis, applied to every landmark before any drawing call.
# MediaPipe landmark for, say, the left knee
lm = results.pose_landmarks.landmark[mp_pose.PoseLandmark.LEFT_KNEE]

h, w, _ = frame.shape # frame height and width in pixels

knee_px = (int(lm.x * w), int(lm.y * h)) # → e.g. (382, 540)

# Repeat for hip and ankle — these three points define the knee angle
hip_px = (int(hip_lm.x * w), int(hip_lm.y * h))
ankle_px = (int(ankle_lm.x * w), int(ankle_lm.y * h))
⚠
