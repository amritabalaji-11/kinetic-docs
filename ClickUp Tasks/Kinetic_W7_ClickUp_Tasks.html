S2-W7-08
Haiku Prompt Engineering — Analysis + Coaching (Two-Section Structure)
To DoHighSquad 2
▼
Description

Write and iterate the Haiku Call 1 prompt. This is distinct from the technical assembly (S2-W7-05) — this task is about the content and structure of what Haiku is asked to do and how each data input is used. The goal is a prompt that reliably returns the full output schema with accurate, specific, and actionable coaching.

Recommended prompt structure:

System prompt — role + rules + output schema
• Role: "You are a biomechanics analyst and sports coach specialising in Goblet Squat technique."
• Part 1 rules: fault detection thresholds, how to use gold standard for comparison, what constitutes valgus/depth/lean fault, walk-in/walk-out exclusion logic
• Part 2 rules: coaching tone (second person, specific — reference actual rep numbers and measured values), causal chain logic, how to use session history for longitudinal context
• Output schema: exact JSON with all required fields and type constraints
• Failure mode reminders: faults_detected must be object not array, all 4 parameter fields must be present even if no fault, do not invent positives

User message — all data inputs, clearly labelled
• [IMAGE] 8-frame composite grid (composite_grid_b64)
• [CURRENT SESSION] exercise_name, weight_value, weight_unit + biomechanics JSON
• [GOLD STANDARD] elite trainer reference JSON from Supabase — same schema as current session. Use for direct angle comparison per rep
• [SESSION HISTORY] last 3 sessions: weight + biomechanics JSON + past Haiku coaching output. Use to detect persistent faults, improvement trends, and progression readiness
• [COACHING CONTEXT] curated .md file content — coaching language, Goblet Squat form cues, fault-specific drills. Use for feedback and recommendation wording
• [TASK] "Analyse this Goblet Squat session. Part 1: identify faults with evidence. Part 2: write coaching for each parameter."

Key prompt engineering rules:

  • Specificity over generics — every observation must reference actual rep numbers and measured values from the biomechanics JSON. "Knee valgus on reps 3–8" not "knee valgus present"
  • Causal chain — if multiple faults co-exist, identify root cause and chain them. e.g. ankle restriction → forward lean → depth deficit
  • Gold standard comparison — for each fault, compare user's actual angles to gold standard ranges. "Your knee angle at bottom: 142° / Gold standard: 88–95°"
  • Session history use — if valgus appeared in previous sessions too, Haiku should say so. "This has appeared across your last 2 sessions at this weight."
  • Walk-in/walk-out — if first or last rep duration ≥ 3× median, exclude from analysis but include in rep_count
  • Affirmation must be earned — do not invent positives if none are present. If a parameter has no clear strength, skip affirmation or note consistency
Acceptance Criteria
  • System prompt clearly separates Part 1 (analysis rules) from Part 2 (coaching rules) and output schema
  • All 6 data inputs are clearly labelled in the user message so Haiku knows what each block is for
  • Test on 3 videos with known faults — Haiku correctly identifies: (1) knee valgus session, (2) insufficient depth session, (3) excessive forward lean session
  • Coaching observations reference actual rep numbers and measured values — not generic advice
  • All 4 parameter fields populated (affirmation, observation, feedback) even when parameter has no fault
  • causal_chain populated correctly when multiple faults co-exist
  • PM reviews 3 outputs and confirms coaching language is specific and actionable
