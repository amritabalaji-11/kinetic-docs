S2-W8-05
Error Handling + Retry Logic
HIGH
Goal
Implement robust error handling and intelligent retry mechanisms for async jobs (Haiku Call 2 and OpenCV Part 2). Ensure failed jobs recover gracefully, frontend receives actionable error information, and operators observe failure patterns via structured logging.
Current State Problem
✗ No retry logic — jobs fail once and stay failed
✗ No error categorization — frontend doesn't know if "try again" or "need new video"
✗ No fallback strategies — single point of failure (S3 .md file fetch blocks entire job)
✗ No structured logging — ops can't see failure patterns

Impact: If Haiku Call 2 times out or OpenCV hits transient GCS error, job fails permanently. Frontend shows error but can't distinguish retryable vs. non-retryable.
Error Categories & Retry Strategy
Haiku Call 2 — 3 Retries (1s → 3s → 9s exponential backoff)
  • Retryable: APITimeoutError, RateLimitError (429), APIStatusError (5xx), IntegrityError (DB lock)
  • Non-Retryable: JSONDecodeError, KeyError (missing fields), context_window_exceeded, wall-clock >120s, other DatabaseError
  • Expected (No Retry): NO_PREVIOUS_SESSION (first session — show empty state)
  • Fallback: S3 coaching fetch fails → use generic coaching (job continues, lower quality)
OpenCV Part 2 — 2 Retries (2s → 5s backoff) [Non-Blocking]
  • Retryable: GoogleAPICallError (timeout/5xx), rare cv2 race conditions
  • Non-Retryable: cv2.error (frame extraction/annotation), persistent GCS auth failure, wall-clock >60s, DB write error
  • Key: All OpenCV failures are non-blocking — Tab 1 coaching visible, image placeholder empty
Timeout Enforcement
  • Haiku Call 2: 120s wall-clock hard limit + 45s per API call timeout
  • OpenCV Part 2: 60s wall-clock hard limit + 30s GCS upload, 10s S3 fetch per-op timeouts
  • Hard timeouts are NOT retryable: If wall-clock exceeded, fail immediately (don't retry)
Exception → Error Code Mapping
Haiku Call 2
  • APITimeoutError → HAIKU_CALL_2_TIMEOUT (retryable)
  • RateLimitError (429) → HAIKU_CALL_2_API_ERROR (retryable)
  • APIStatusError (5xx) → HAIKU_CALL_2_API_ERROR (retryable)
  • JSONDecodeError → HAIKU_CALL_2_INVALID_OUTPUT (NOT retryable)
  • KeyError (missing field) → HAIKU_CALL_2_INVALID_OUTPUT (NOT retryable)
  • BadRequestError ("context_window_exceeded") → HAIKU_CALL_2_CONTEXT_OVERFLOW (NOT retryable)
  • IntegrityError (DB lock) → HAIKU_CALL_2_DB_WRITE_ERROR (retryable)
  • Other DatabaseError → HAIKU_CALL_2_DB_WRITE_ERROR (NOT retryable)
  • Wall-clock >120s → HAIKU_CALL_2_TIMEOUT (NOT retryable)
OpenCV Part 2
  • GoogleAPICallError (timeout/5xx) → OPENCV_GCS_WRITE_ERROR (retryable)
  • GoogleAPICallError (403/401) → OPENCV_GCS_WRITE_ERROR (NOT retryable)
  • cv2.error (frame extraction) → FRAME_EXTRACTION_FAILED (NOT retryable)
  • cv2.error (draw/annotation) → ANNOTATION_FAILED (NOT retryable)
  • DefaultCredentialsError → OPENCV_GCS_WRITE_ERROR (NOT retryable, auth issue)
  • DatabaseError (write failed) → OPENCV_DB_WRITE_ERROR (NOT retryable)
  • Wall-clock >60s → OPENCV_TIMEOUT (NOT retryable)
Implementation Phases
Phase 1: Error Categorization (Day 1)
  • Define map_exception_to_error_code() function in errors.py
  • Map all exception types → (error_code, is_retryable) tuple
  • Unit tests: 10+ test cases covering each error type
Phase 2: Retry Loop Implementation (Day 1–2)
  • Implement main job execution loop with retry logic
  • Add backoff delays: 1s, 3s, 9s for Haiku; 2s, 5s for OpenCV
  • Enforce timeout at job start + each operation
  • Log every state change: queued, started, attempt N, retrying, success, failure
Phase 3: Fallback Strategies (Day 2)
  • Implement S3 coaching content fallback
  • If S3 fails → use generic coaching prompt (non-blocking)
  • Add DEFAULT_COACHING_BY_FILE constants for 3+ coaching files
Phase 4: Structured Logging (Day 2–3)
  • Every error: log job_id, error_code, exception_type, attempt, elapsed_seconds, full traceback
  • Route to CloudLogging with severity level (INFO/WARNING/ERROR)
  • Exclude PII (no video URLs, user data)
  • Create CloudLogging dashboard: queryable by error_code, job_type, analysis_id
Phase 5: Integration & Testing (Day 3)
  • Wire into job_runner.py (S2-W8-02)
  • Ensure status endpoint returns error_code (S2-W8-03)
  • Ensure job_failed SSE event includes error_code + retryable (S2-W8-04)
  • End-to-end test: upload video, simulate job failure, verify SSE event + error message
Key Design Decisions
  • Why 3 retries for Haiku, 2 for OpenCV? Haiku Call 2 blocks Tab 2 (critical path) — worth more retries. OpenCV is non-blocking — faster to fail gracefully.
  • Why fallback for S3 coaching, not fail? Coaching enriches recommendations but isn't required. Better to serve degraded recommendations than fail entirely.
  • Why hard timeout at 120s/60s? User shouldn't wait indefinitely. Hard stop ensures bounded latency.
  • Why "partial" retryable for OpenCV errors? Tab 1 coaching always visible. Image is nice-to-have, not blocking. Don't prevent user from reading analysis.
Acceptance Criteria
  • All exception types → error_code mapping correct (Haiku + OpenCV)
  • Retryable vs. non-retryable categorized correctly for each error
  • Haiku: 3 retries with 1s, 3s, 9s backoff for retryable errors
  • OpenCV: 2 retries with 2s, 5s backoff for retryable errors
  • Non-retryable errors fail immediately (no retry attempt)
  • Hard timeout enforced: Haiku at 120s, OpenCV at 60s — no retry on timeout
  • Per-operation timeouts set: Haiku API 45s, GCS 30s, S3 10s
  • S3 coaching unavailable → generic coaching used (job continues)
  • Every error logged: job_id, error_code, exception_type, attempt, elapsed_seconds, traceback
  • CloudLogging dashboard queryable by error_code, job_type, analysis_id
  • Frontend receives { error_code, error_message, retryable } in error responses
  • job_failed SSE event includes job_type to identify which job failed
  • Error message never shown to user (internal log only) — frontend maps error_code to message
  • OpenCV failures don't block Tab 1 (coaching visible, image placeholder empty)
  • Manual E2E test: upload video, job fails, error surfaces on frontend with correct message
Testing Checklist
Unit Tests: Exception → error_code mapping (20+ error types) · Timeout detection · Backoff calculation · Fallback on S3 failure

Integration Tests: Haiku timeout (retry succeeds) · All 3 retries fail → job_failed event · OpenCV GCS failure (2 retries) → success · Hard timeout (no retry) · S3 unavailable → generic coaching

Manual E2E Tests:
  • Upload video → both jobs succeed → SSE progress events
  • Haiku timeout (retry succeeds) → observe 1s sleep + retry → Tab 2 shows recommendations
  • OpenCV GCS failure (retries fail) → Tab 1 visible, image placeholder empty
  • S3 coaching unavailable → generic coaching used → Tab 2 shows recommendations
  • Hard timeout (>120s) → immediate failure, no retry
Frontend Integration
Squad 1 must handle:
  • Consume job_failed SSE event with job_type + error_code + retryable
  • For job_type: "haiku_call_2" failures: show error in Tab 2 · retryable="true" → "Try again" button · retryable="false" → "Re-film and upload" button
  • For job_type: "opencv_part_2" failures: keep Tab 1 visible (non-blocking) · show inline warning or keep placeholder · no blocking CTA
  • Map error_code to user-facing message (from FE_SSE_and_Errors.md error lookup table)
  • Never display error_message field (internal log only)
