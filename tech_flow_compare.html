Option A — What the layer grouping reveals
→ 5 distinct architectural tiers — clear separation of UI, API, compute, AI, and data concerns
→ Layer 2 (Backend/API) is the orchestrator — it touches every other layer, making it the highest integration risk
→ The Processing → AI boundary is where the most data flows across — biomechanics JSON + frames + quality gate status + RAG + user history all converge here
→ RAG ingestion is genuinely offline — it has no live-path connection to Layer 1 (UI), which is correct

Section 2 — Feature decisions
What we're keeping, simplifying, and dropping — and why
Feature / Component Decision What remains Why
Core AI Pipeline
Video upload + GCS storagePOST /upload → GCS → analysis_id Kept Unchanged. Video stored at GCS path, form_sessions record written, SSE stream opened. Entry point to the entire product. Cannot be cut.
MediaPipe pose extraction + quality gateLandmarks, rep segmentation, visibility scoring Kept Unchanged. Quality gate rejects bad-angle videos before processing starts. Foundation of all downstream analysis. No pipeline without it.
OpenCV Part 1 — overlay videoFull video with green skeleton lines Kept Already built. Full video with skeleton overlay saved to GCS as overlay_video_url. Biomechanics JSON + 8-frame composite grid sent to Haiku Call 1. Nemotron removed after W6 A/B test.
Biomechanics scriptKnee, hip, ankle angles · tempo · stability Kept Unchanged. Requires adding bottom_frame + bottom_timestamp_ms per rep (data gap fix). Structured input for Haiku Call 1. Also used for gold standard comparison and OpenCV Part 2 annotation.
Claude Haiku 4.5 — Call 1Biomechanics JSON + 8-frame composite → form analysis + coaching (single call — Nemotron removed after W6 A/B test) Kept Unchanged. Receives overlay_video_url + biomechanics JSON. Returns per-rep scores, issues, chain-of-thought. Core AI layer. Differentiator vs single-rep competitors.
OpenCV Part 2 — annotated overlayWorst rep · camera angle detection (side/front) · skeleton + fault panel · gold standard reference lines Kept — Option 3 Skeleton lines + joint markers + actual angles + gold standard text. ~70% already built from Part 1. Estimated 3–4 days remaining. Key Results screen visual. Shows user exactly what went wrong on their worst rep.
Claude Haiku 4.5 — Call 2 (async)Current session + 5-session history → longitudinal progression coaching for Tab 2 Kept Haiku Call 2 receives current session (from DB) + last 5 sessions + coaching output. Returns longitudinal progression coaching for Tab 2. + weight recommendation. User-facing output. The "coach" experience. Cannot be cut.
RAG · Grounding
RAG — coaching style + language groundingPurpose: ground Claude's language, not analysis Simplified 5–10 curated documents (PT coaching language, form cues, goblet squat references) converted to MD files and injected directly into Claude's system prompt. No retrieval. No embeddings. 1 exercise + <10 documents = system prompt injection is sufficient. Saves 3+ weeks of Squad 3 infra work.
Vector DBPinecone / Weaviate / pgvector Dropped Not built for MVP. Architecture documented for future milestone when >1 exercise is added. Not needed for <10 documents. Adds significant setup, cost, and operational complexity for no gain at this scale.
Embedding model + ingestion pipelineChunking, metadata tagging, vector indexing Dropped Not built. MD files need no chunking — they go directly into the prompt. Chunking is a vector DB concept. Irrelevant when using system prompt injection.
Gold Standard
Gold standard biomechanicsReference angles for comparison + overlay Kept 3–5 good-form Goblet Squat videos run through MediaPipe + biomechanics script. Outputs stored in gold_standard_biomechanics table. Used by OpenCV Part 2 overlay and Claude system prompt as reference values. W6: data prep. W7: integrated into pipeline. Grounds angle comparisons in real biomechanics data rather than hardcoded values. More credible for demo and accuracy validation.
Authentication · User Identity
Authentication — JWT + Supabase AuthSign up, login, session management Dropped Not built for demo. No login screens, no JWT middleware, no auth endpoints. Adds ~1.5 weeks of Squad 2 + Squad 1 work with zero demo value. Can be added post-demo.
User identity for form comparisonPersistent user_id across sessions Simplified 2–3 user IDs hardcoded in the DB. Frontend sends a fixed user_id on all requests. Form comparison, session history, and progression work as normal. Same demo outcome — multiple sessions per user, progression visible — without any auth infrastructure.
Frontend Screens
Results screenForm score, coaching, worst-rep frame, rep chart Kept Full build. Real data from pipeline. Worst-rep annotated frame shown. Coaching output from Claude. Progression recommendation chip. Primary product screen. The moment the user sees value. Must be real, not dummy.
Dashboard + Session HistoryProgression trend, form score over time, weight vs form Kept Real build using 2–3 seeded user IDs with pre-loaded session history. Shows form score trend, weight progression, per-parameter trends. The product story — not just one analysis but the journey over time. Seeded data makes it compelling from day one of the demo.
Workout LoggerLog sets, reps, weight · link to form sessions Simplified This helps with progression recommendation logic. For today's demo, we've reducing scope to just frontend with dummy data. No backend endpoints. Required for the progression recommendation to be meaningful.
Auth screens — Login + Sign upOnboarding flow, form fields, validation Dropped Not built. Demo starts directly on the Upload screen. No auth system to connect to. Screens have no function without backend auth.
Profile / Preferences screenName, training frequency, injury notes Frontend shell only Screen exists and is routable. Displays dummy data. No backend endpoints. Not interactive. Shows product completeness in demo without requiring backend work. Backend endpoints deferred post-demo.
