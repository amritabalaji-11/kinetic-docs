S2-W8-02
Haiku Call 2 — Async Job Pipeline
HIGH
Description
Implement the complete async job pipeline for Haiku Call 2. This runs in the background after Haiku Call 1 completes, generating weight progression recommendations and personalized coaching.
  • Job Trigger: When POST /upload completes (Haiku Call 1 done), immediately enqueue Cloud Tasks job for this analysis_id
  • Job Worker Process:
    1. Fetch form_analysis_results record for analysis_id
    2. Query database for past 3 sessions for same user + exercise
    3. Fetch 5–10 .md coaching files for progression context from S3
    4. Assemble Haiku Call 2 prompt: current form score + weight + past session data + coaching cues
    5. Call Claude Haiku 4.5 API with structured prompt
    6. Parse response: progression_recommendation + coaching_output
    7. Store result in form_analysis_results.haiku_call_2_output
    8. Update job_status to 'complete', set completed_at timestamp
  • Job timeout: 120 seconds maximum. If exceeds, mark as timeout
  • Implement logging at each step for debugging
Acceptance Criteria
  • Cloud Tasks job enqueued immediately when POST /upload completes
  • Job status transitions correctly: queued → running → complete
  • Past 3 sessions retrieved correctly from database
  • MD coaching files loaded from S3 without errors
  • Haiku 4.5 API called with complete context (current + history + coaching)
  • Progression recommendation and coaching output stored in haiku_call_2_output JSONB
  • Job completes within 120 seconds (test with realistic video sizes)
  • If timeout, job_status marked as 'timeout' with error message
  • Logs show job start, context fetch, API call, result storage (all timestamps)
  • Test with at least 3 different form videos to confirm end-to-end flow
Dependencies
DEPENDS ON S2-W8-01 (Schema updated with job columns)

S2-W8-05
Error Handling + Retry Logic
HIGH
Description
Implement robust error handling and retry mechanisms for the async job pipeline. Ensures failed jobs are retried intelligently and frontend gets meaningful error messages.
  • Haiku API Failures: Implement 3-retry strategy with exponential backoff (1s, 3s, 9s delays)
  • Job Timeout: Hard stop at 120 seconds, mark as timeout, emit haiku_call_2_failed event
  • Database Write Failures: Log error, alert ops, mark job as failed with error_code
  • MD File Fetch Failures: Retry S3 read, fallback to generic coaching if unavailable
  • Frontend Error Response: Return { error_code, error_message, retryable (bool) } so frontend knows whether to show "try again" button
  • Logging: Log all failures with context (attempt #, error type, full stack trace)
  • UI Fallback: If job fails, Progression Page shows "Unable to generate recommendation" instead of hanging
Acceptance Criteria
  • Failed Haiku API call triggers 3 retries with 1s, 3s, 9s delays
  • If all 3 retries fail, job marked as failed, haiku_call_2_failed event emitted
  • Job timeout enforced at 120 seconds (test with simulated slow processing)
  • Timeout triggers haiku_call_2_failed event with error_code = "timeout"
  • DB write failures logged with full stack trace
  • S3 read failures caught, fallback to generic coaching text (doesn't block job)
  • Frontend receives { error_code, error_message, retryable } in error responses
  • All failures logged to CloudLogging with severity level
  • Progression Page gracefully shows error message when job fails
  • Manual retry possible (S2 or frontend can retry failed jobs)
