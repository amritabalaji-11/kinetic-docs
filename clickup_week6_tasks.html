S1-W6-08
Pre-upload client-side validation — file checks before POST /upload is sent  NEW
Dependencies
Needs → S1-W5-08 / S1-W6 carry-over (Upload screen built — validation lives on this screen)
Unblocks → S2-W6-01 (server never receives invalid files — saves backend error overhead)
Description
Before the user's video is sent to the backend, S1 validates it client-side. These checks run in the browser — no SSE, no server call. If validation fails, show an inline error on the Upload screen with a specific message per failure type. Full error copy: FE_SSE_and_Errors.md Section 4 — Pre-upload. Four checks to implement:

1. FILE_TOO_LARGE — file size > 500 MB. Message: "That video is too large (max 500 MB). Try trimming it to your working set." CTA: dismiss, re-select file.
2. FORMAT_UNSUPPORTED — MIME type not .mp4 / .mov / .avi. Message: "We can't read that format. Export as MP4 and try again." CTA: dismiss, re-select file.
3. FILE_CORRUPT — zero bytes or unreadable header. Message: "That file looks corrupted. Re-export from your camera roll and try again." CTA: dismiss.
4. UPLOAD_TIMEOUT — network drops mid-transfer. Message: "Upload timed out. Check your connection and try again." CTA: "Try again" (re-submits same file).

All four checks must complete before the POST /upload request is sent. The Submit button must not be tappable while validation is running.
Acceptance Criteria

  • ✓ UPLOAD_TIMEOUT: network drop mid-transfer shows correct error with "Try again" CTA that re-submits
  • ✓ Valid file passes all checks and proceeds to POST /upload — no false positives

What Squad 2 builds — the full sequence
Once the function contract is agreed, Squad 2 wires everything together in this order:

Step 1 — POST /upload: Accept multipart (video + exercise_id + weight_value + weight_unit + user_id + session_id). Save video to GCS → generate analysis_id → write form_analyses to DB (status: uploaded) → return {analysis_id} immediately. Emit upload_received SSE.

Step 2 — Async background task: UPDATE form_analyses status → "processing". Emit mediapipe_started SSE. Call Squad 3's process_video(gcs_path, analysis_id).

Step 3 — Handle return:
  • If status == "failed": UPDATE form_analyses status → "failed". Emit full error SSE: { analysis_id, session_id, user_id, error_code, error_stage, retryable, message }.
  • If status == "success":
    1. UPDATE form_analyses: quality_gate_status + video_score (from process_video return)
    2. INSERT form_analysis_results: biomechanics_json (raw measurements — angles, timing, rep segments) + rep_count. Score fields (overall_form_score, posture_score etc.) are NOT written here — biomechanics produces raw data, not scores. Nemotron writes scores in W7.
    3. Emit biomechanics_complete SSE
    4. W6 scope: emit analysis_complete SSE immediately — acts as pipeline end signal so S1 navigates to Results screen. Moves later in W7+ when Nemotron + Claude are wired.
    5. UPDATE form_analyses status → "complete"

Step 4 — Serve results: GET /analysis/{id}/result returns the FE_Response_Schemas.md shape. In W6: rep_count and quality_gate_status are populated; overall_score and all parameter scores are null (biomechanics produces raw measurements, not scores — Nemotron generates scores in W7); coaching, progression_recommendation, annotated_frame_url are null. S1 renders what is non-null and shows placeholder states for null fields. Same endpoint shape throughout — fields fill in as W7/W8 pipeline stages are wired.
Overall done when
  • ✓ Real video uploaded → GCS stored → biomechanics pipeline runs → SSE events fire in correct sequence → Results screen shows rep_count + quality_gate_status. Score fields (overall_score etc.) are null in W6 — scores come from Nemotron in W7, not biomechanics.
