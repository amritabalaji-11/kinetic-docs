US-04 Video Submission
W6▶
As a user ready to analyse my form, I want to select my exercise, enter my weight, and upload a video, so that Kinetic can analyse my session.
Upload screen includes an inline filming tips section — a reference image showing correct camera angle for Goblet Squat + 3–4 short copy tips. Always visible before the user picks a file. Filming tips are part of this screen, not a separate flow.
Acceptance Criteria
  • Given I'm on the Upload screen, I see an inline filming guide — a reference image and 3–4 tips on camera angle, distance, height, and clothing
  • Given I'm on the Upload screen, I can select Goblet Squat and enter my weight in kg
  • Given I select a video file (.mp4 / .mov), I see the filename and size confirmed
  • Given all fields are complete, the Submit button becomes active
  • Given the file is unsupported or over 500MB, I see a clear inline error
  • POST /upload fields: video (file) · exercise_id = "ex_gob_squat_001" · weight_value (float) · weight_unit = "kg"
US-05 Analysis Processing & Quality Gate Errors
W6▶
As a user who just submitted a video, I want to see a clear processing status — and if my video is rejected, an error that tells me exactly what went wrong and how to fix it when I re-film.
Processing
  • Given I submit a video, I see a live progress indicator with stage labels (e.g. "Reading your movement patterns…") — not a blank screen
  • Given processing completes, I'm automatically taken to the Results screen
Quality Gate — contextual errors per rejection reason
  • Bad angle → "Try filming from a 45° side angle so your full body is visible"
  • Poor visibility → "Try fitted clothing and a well-lit space"
  • Partial occlusion → "Step back so your full body from head to toe is in frame"
  • Too few reps → "We need at least 3 complete reps — film a longer set"
  • Given any rejection, a "Try again" button returns to Upload with filming tips visible
US-06a Analysis Results — Score, Parameters & Rep Chart
W6 → W7▶
As a gym-goer training alone, I want to see my overall form score, a breakdown across 4 parameters, a personalised summary, and my rep-by-rep progression, so I immediately understand how I performed and what to prioritise.
W6: Results screen built against dummy data. W7: Real pipeline output wired — confirmed deliverable, not optional.
Results screen delivers
  • Overall score /100 — prominently at the top
  • 1–2 sentence personalised summary — combines form quality with the weight used
  • 4 parameters — Posture · Stability · Movement Quality · Tempo. Each shows: score / what they're doing well (1 sentence) / what's off (1 sentence) / action to work on
  • Rep-by-rep chart — visualises form from first to last rep, showing where breakdown begins
US-06b Visual Proof of Form
W7▶
As a user viewing my results, I want to see a video or image of me doing the exercise with joint angles visible, so I can see exactly where my form broke down on my own body.
Acceptance Criteria
  • Given analysis is complete, I see a visual of my form — image or video — with joint angles visible on my own body
  • Given the visual, joint markers are colour-coded by status: green (in range) · amber (borderline) · red (outside range)
  • Given each joint, I see my actual angle and the gold standard range — e.g. "Knee: 88° · Ideal: 80–95°"
  • Given I'm on mobile web, the visual is full-width and labels are legible without zooming
US-07 Weight-Specific Coaching & Joint Corrections
W7▶
As a user, I want coaching that is specific to the weight I was lifting and the joint issues detected, so I know exactly what to fix at this load — not generic advice.
Acceptance Criteria
  • Given analysis is complete, I see minimum 2 specific joint-level corrections (e.g. "Ankle dorsiflexion limits your depth from rep 5 onwards")
  • Given multiple sessions exist at different weights, coaching references weight history — e.g. "Your form at 12kg has held for 3 sessions — ready for 14kg"
  • Coaching is specific to what was observed, not generic — generic output is a fail state

US-08 Form Comparison & Progression Recommendation
W8▶
As a user who has logged multiple sessions, I want to compare my current form against my previous session on the same 4 parameters, and receive a weight progression recommendation, so I can see whether I'm improving and whether to go heavier.
Weight history (past sessions, weights used, form scores) is retrieved from the DB and passed to Claude Sonnet → Claude Haiku 4.5 — Call 2 (async) (W6 A/B test) — not Nemotron. Nemotron analyses the current video. Claude synthesises coaching and the progression recommendation using historical context.
Acceptance Criteria
  • Given I'm on the Results screen, I see a Form Comparison view alongside my current results
  • Given I have a previous session, I see a side-by-side breakdown: session date + weight, overall score, 4 parameter scores, visual proof, rep chart — for current and previous session
  • Given no previous session, I see: "Log more sessions to see your progression"
  • Given multiple sessions, the progression recommendation (ready / hold / drop) references specific past sessions by weight

Section 3
Scope Decisions
Key decisions made to protect the demo and reduce risk — with plain-language reasoning.
Auth
No authentication — hardcoded demo users
2–3 user IDs seeded in the DB. App opens with a user selection screen (proxy for auth). Frontend sends selected user_id as a header. Form comparison, session history, and dashboard all work as expected.
Why: Auth adds significant Squad 1 + Squad 2 build effort with zero demo value. The user selector enables switching between demo users to show different progression stories — more compelling than a single user with limited history.
RAG
Vector DB dropped — MD files in Claude system prompt
5–10 curated coaching documents converted to MD files and injected directly into Claude Sonnet → Claude Haiku 4.5 — Call 2 (async) (W6 A/B test)'s system prompt. No retrieval endpoint, no embeddings, no ingestion pipeline.
Why: 1 exercise + <10 documents = system prompt injection is sufficient. Vector DB adds significant Squad 3 infrastructure with no meaningful quality gain at this scale.
Visual proof
Text coaching ships W6, visual proof ships W7
W6: Results screen shows real biomechanics data + basic Nemotron output. W7 confirmed deliverable: visual proof of form (image or video with joint angles) + full Claude coaching.

OpenCV — what's already built (W5): The developer built a full video overlay with green skeleton lines, joint dots, angle values (Hip, Knee, Back), rep counter, and state detection. This overlay video is what gets sent to Nemotron.

W7 addition: After Nemotron identifies the worst-performing rep, the pipeline extracts a still frame from the raw video at that moment. The existing overlay drawing code is reused to annotate it with actual vs gold standard angles. This image is shown to the user on the Results screen. Estimated 3–4 days to build since the core drawing work is already done.
Why: Reuses 70% of already-built code. Delivers the same user value. Showing someone their own body is more powerful than any score — this is the product moment.
Workout Lifecycle
Frontend only — no backend, no AI
Workout Builder + Tracker are built as a frontend experience only. No data is saved, no backend integration, no AI. Built to show users the full product vision and improve overall app feel.
Why: Frontend capacity is committed to the core demo screens. The Workout Lifecycle adds product depth for the demo without engineering cost. The limitation is invisible to the viewer.
Profile
Profile screen — frontend shell only
Profile screen exists and is routable. Displays dummy data. No save functionality, no backend endpoints. Auth dropped means no onboarding flow to collect initial profile.
Why: Removes backend profile endpoints from Squad 2's W8 scope. Showing the screen signals intent — personalisation wired to AI coaching is a post-demo feature.
Latency
Target 30–35s end-to-end
End-to-end pipeline latency target: under 35 seconds. While processing, the presenter narrates what the AI is doing at each stage — turning the wait into a credibility moment. If latency exceeds 35s by W9, a pre-recorded backup is prepared.
Why: 35s is realistic for the full pipeline — MediaPipe, OpenCV overlay, Biomechanics, Nemotron, Claude coaching. Narration makes it compelling regardless.
