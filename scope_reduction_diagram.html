Section 2 — Feature decisions
What we're keeping, simplifying, and dropping — and why
Feature / Component Decision What remains Why
Core AI Pipeline
Video upload + GCS storagePOST /upload → GCS → analysis_id Kept Unchanged. Video stored at GCS path, form_sessions record written, SSE stream opened. Entry point to the entire product. Cannot be cut.
MediaPipe pose extraction + quality gateLandmarks, rep segmentation, visibility scoring Kept Unchanged. Quality gate rejects bad-angle videos before processing starts. Foundation of all downstream analysis. No pipeline without it.
OpenCV Part 1 — overlay videoFull video with green skeleton lines Kept Already built. Full video with skeleton overlay saved to GCS as overlay_video_url. This is what goes into Nemotron. Confirmed more accurate than raw video.
Biomechanics scriptKnee, hip, ankle angles · tempo · stability Kept Unchanged. Requires adding bottom_frame + bottom_timestamp_ms per rep (data gap fix). Structured input for Nemotron. Also used for gold standard comparison and frame extraction.
Nemotron 3 Nano OmniOverlay video + biomechanics JSON → per-rep scoring Kept Unchanged. Receives overlay_video_url + biomechanics JSON. Returns per-rep scores, issues, chain-of-thought. Core AI layer. Differentiator vs single-rep competitors.
OpenCV Part 2 — frame extractionWorst-rep still image with angle overlay Kept — Option 3 Skeleton lines + joint markers + actual angles + gold standard text. ~70% already built from Part 1. Estimated 3–4 days remaining. Key Results screen visual. Shows user exactly what went wrong on their worst rep. Feasible given Part 1 foundation.
Claude Sonnet — coaching outputNemotron output + grounding → coaching + progression Kept Unchanged. Receives Nemotron output + MD file context via system prompt. Returns coaching paragraphs + weight recommendation. User-facing output. The "coach" experience. Cannot be cut.
RAG · Grounding
RAG — coaching style + language groundingPurpose: ground Claude's language, not analysis Simplified 5–10 curated documents (PT coaching language, form cues, goblet squat references) converted to MD files and injected directly into Claude's system prompt. No retrieval. No embeddings. 1 exercise + <10 documents = system prompt injection is sufficient. Full vector DB is overkill at this scale. Saves 3+ weeks of Squad 3 infra work.
Vector DBPinecone / Weaviate / pgvector Dropped Not built for MVP. Architecture documented for future milestone when >1 exercise is added. Not needed for <10 documents. Adds significant setup, cost, and operational complexity for no gain at this scale.
Embedding model + ingestion pipelineChunking, metadata tagging, vector indexing Dropped Not built. MD files need no chunking — they go directly into the prompt. Chunking is a vector DB concept. Irrelevant when using system prompt injection.
Gold Standard
Gold standard biomechanicsReference angles for comparison + overlay New · added 3–5 good-form Goblet Squat videos run through MediaPipe + biomechanics script. Outputs stored in gold_standard_biomechanics table in PostgreSQL. Used by OpenCV Part 2 overlay and Claude system prompt as reference values. W6: data prep. W7: integrated into pipeline. Grounds angle comparisons in real biomechanics data rather than hardcoded values. More credible for demo and accuracy validation. Low effort since the pipeline to produce the data is already being built.
Authentication · User Identity
Authentication — JWT + Supabase AuthSign up, login, session management Dropped Not built for demo. No login screens, no JWT middleware, no auth endpoints. Adds ~1.5 weeks of Squad 2 + Squad 1 work with zero demo value. Judges are not evaluating login flows. Can be added post-demo.
User identity for form comparisonPersistent user_id across sessions Simplified 2–3 user IDs hardcoded in the DB (e.g. user_001, user_002, user_003). Frontend sends a fixed user_id on all requests. Form comparison, session history, and progression work as normal. Achieves the same demo outcome — multiple sessions per user, progression visible — without any auth infrastructure. Sufficient for a controlled demo environment.
Frontend Screens
Results screenForm score, coaching, worst-rep frame, rep chart Kept Full build. Real data from pipeline. Worst-rep annotated frame shown. Coaching output from Claude. Progression recommendation chip. Primary product screen. The moment the user sees value. Must be real, not dummy.
Dashboard + Session HistoryProgression trend, form score over time, weight vs form Kept Real build using 2–3 seeded user IDs with pre-loaded session history. Shows form score trend, weight progression, per-parameter trends. Demonstrates Kinetic's longitudinal data differentiator. This is the product story — not just one analysis but the journey over time. Seeded with hardcoded user IDs so it's compelling from day one of the demo without needing 4 weeks of real usage data.
Workout LoggerLog sets, reps, weight · link to form sessions Kept Kept — feeds progression recommendation logic. User logs weight used → pipeline uses it for "ready to progress" decision. Required for the progression recommendation to be meaningful. Without weight history, Claude cannot say "your form at 12kg is solid — try 14kg."
Auth screens — Login + Sign upOnboarding flow, form fields, validation Dropped Not built. Demo starts directly on the Upload screen. No auth system to connect to. Screens have no function without backend auth.
Profile / Preferences screenName, training frequency, injury notes Frontend shell only Screen exists and is routable. Displays dummy data. No backend endpoints. Not interactive. Shows product completeness in demo without requiring backend work. Low effort for Squad 1 — reuse existing component patterns. Backend endpoints deferred post-demo.
